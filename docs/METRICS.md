# 핵심 지표

`/metrics`는 가입부터 선정까지의 흐름과 PG사 응답을 주 단위로 보여준다. 기존 대시보드(`/`)는 오늘 처리할 운영 대기열이고, 이 화면은 사업이 자라는지 보는 곳이다.

서포트비는 구독 서비스가 아니라 구매사와 PG사를 잇는 마켓플레이스다. 구매사 한 곳의 거래는 수년에 한 번이므로 MRR이나 구독 해지율 대신 **퍼널 전환과 매칭**을 본다. 표본이 작은 동안에는 비율이 한두 건에 크게 흔들린다. 화면은 주간 원시 건수를 먼저 보여주고, 비율은 항상 `분자/분모`로 쓰며 분모가 10 미만이면 퍼센트를 붙이지 않는다.

## 집계 기준

- **시간.** 날짜와 주는 한국 시간이다. 주는 월요일에 시작하고, 끝나지 않은 주는 "진행 중"으로 표시한다.
- **요청 발송 시각.** `rfps.sent_at`을 쓰고, 비어 있으면 그 요청의 첫 초대 시각(`rfp_invitations.sent_at`)으로 대신한다. 초안(`status = 'draft'`)은 세지 않는다.
- **견적 수신.** 초안이 아닌 견적(제출 + 철회)을 받은 것. 재견적 회차는 같은 요청·같은 PG사로 묶어 한 번만 센다.
- **종결된 요청.** 마감이 지났거나 선정·취소·마감 처리된 요청. 비율의 분모에는 종결된 요청만 넣고, 진행 중인 요청은 건수로 따로 적는다.
- **활동.** 사람이 직접 한 행동만 센다. `audit_logs`에서는 허용 목록(`lib/metrics/rules.ts`의 `HUMAN_ACTIONS`)에 있는 행동과 `chat_messages`의 메시지 전송이다. 가입 때 자동으로 남는 기록과 서명 공급자가 남기는 기록은 넣지 않는다.

## 집계에서 빼는 것

| 대상 | 판정 | 빠지는 범위 |
| --- | --- | --- |
| 시스템 계정 | `users.is_system_account` | 활성 사용자 |
| 내부 직원 계정 | 이메일 도메인이 `METRICS_EXCLUDED_EMAIL_DOMAINS`에 있음 | 활성 사용자 |
| 테스트 워크스페이스 | 이름에 `test` 또는 `테스트`가 들어 있음. bidit `lib/features/test-pg.ts`와 같은 규칙이며 부분 문자열이라 상호에 우연히 든 곳도 빠진다 | 모든 지표. 구매사면 그 요청까지, PG사면 그 초대·견적·선정까지 |
| 내부 워크스페이스 | 시스템 계정을 뺀 멤버 전원이 내부 직원 | 테스트 워크스페이스와 같음 |
| 담당자 미합류 PG사 | 시스템 계정이 아닌 승인 멤버가 없는 PG 워크스페이스. 미리 등록해 둔 PG사가 여기에 해당한다 | 신규 PG·활성 PG 수만 |

담당자가 합류하지 않은 PG사라도 요청을 받고 견적이 나갈 수 있다. 그 초대·견적·선정은 구매사 쪽 결과(견적 수신율, 선정률 등)에 그대로 세고, PG사별 현황에는 "담당자 미합류"로 표시해 보여준다.

화면 맨 아래에 제외한 계정·워크스페이스·요청 수를 적는다. 회원·구매사·RFP 목록은 이 규칙을 쓰지 않으므로 건수가 다르다. 같은 자리에 발송 시각이 비어 첫 초대 시각으로 대신한 요청 수와, 발송 시각도 초대도 없어 뺀 요청 수도 적는다. 이 두 숫자가 크면 `rfps.sent_at`을 채우지 않는 발송 경로가 있다는 뜻이다.

`METRICS_EXCLUDED_EMAIL_DOMAINS`는 쉼표로 구분한 도메인 목록이다. 정확히 일치하는 도메인만 내부로 보며, 설정하지 않으면 도메인 기준 제외는 하지 않는다.

## 화면별 정의

### 지난주 요약, 주간 추이

그 주에 일어난 사건의 수다.

| 열 | 정의 |
| --- | --- |
| 신규 구매사 | 그 주에 만들어진 구매사 워크스페이스. 구매사는 가입과 입점 신청이 함께 생긴다 |
| 신규 PG | 그 주에 만들어진 PG 워크스페이스. 미리 등록된 PG사는 첫 담당자가 합류한 주에 센다 |
| 구매사 승인 | 그 주에 승인된 구매사 워크스페이스(가장 이른 승인 시각 기준) |
| 요청 발송 | 그 주에 발송된 요청 |
| 견적 수신 요청 | 그 주에 첫 견적을 받은 요청. North Star 후보 |
| 선정 | 그 주에 선정된 요청 |
| 활성 구매사 · 활성 PG | 그 주에 활동이 있던 워크스페이스 |

### 구매사 퍼널

선택한 기간에 만들어진 구매사 워크스페이스를 한 집단으로 묶어 어디까지 갔는지 따라간다. 각 단계는 앞 단계를 모두 마친 곳만 세므로 뒤로 갈수록 줄어든다.

1. 워크스페이스 생성
2. 이메일 인증: 인증된 멤버가 1명 이상
3. 입점 승인: 승인된 신청이 있음. 신규사업체 자동 승인은 인증보다 먼저 일어날 수 있어, 인증과 승인을 모두 마친 시점을 이 단계의 도달 시각으로 본다
4. 첫 요청 발송
5. 첫 견적 수신
6. 선정

"직전 단계부터 걸린 시간"은 중앙값이다. 조건이 먼저 충족돼 있으면 0으로 센다(이미 인증된 사용자가 새 워크스페이스를 만든 경우 등).

### PG사 응답과 매칭

선택한 기간에 발송된 요청이 대상이다.

| 지표 | 정의 |
| --- | --- |
| 견적 수신율 | 종결된 요청 중 견적을 1건 이상 받은 요청 |
| 선정률 | 종결된 요청 중 선정된 요청 |
| 초대 열람률 | 종결된 요청의 초대 중 `opened_at`이 있는 초대 |
| PG 응답률 | 종결된 요청의 초대 중 그 PG사가 견적을 낸 초대 |
| 무응답 마감 | 견적 없이 종결된 요청 수 |
| 첫 견적까지 걸린 시간 | 발송부터 첫 견적 제출까지의 중앙값(진행 중 요청 포함) |
| 선정까지 걸린 시간 | 발송부터 선정까지의 중앙값 |

### PG사별 현황

선택한 기간에 발송된 요청 기준으로 받은 요청·열람·견적 제출·선정을 센다. 최근 활동일은 마지막 견적 제출일과 조회 범위 안의 활동일 중 늦은 쪽이다.

담당자가 있는 PG사는 모두 보여준다. 담당자가 없는 PG사는 그 기간에 요청을 받았거나 견적·선정이 있을 때만 "담당자 미합류"로 표시해 보여준다. 응답할 사람이 없는 곳으로 요청이 가고 있는지 확인하는 용도다.

### 활성 사용자 (행동 기준)

어제, 최근 7일, 최근 30일에 활동한 사용자와 워크스페이스 수다. 오늘은 아직 끝나지 않아 넣지 않는다.

**접속자 수가 아니다.** 로그인과 화면 조회는 어디에도 기록되지 않는다. `workspace_members.last_seen_at`은 갱신되지 않고, 로그인 성공은 감사 로그에 남지 않으며, 세션은 JWT라 세션 테이블이 없다. 그래서 조회만 한 방문은 빠지고 실제 접속자보다 적게 나온다. 접속 기준 DAU·MAU와 재방문율은 bidit에 일 단위 접속 기록을 추가해야 볼 수 있고, 추가하기 전의 날짜는 소급할 수 없다.

### 가입 유입 경로

퍼널과 같은 워크스페이스를, 만든 사용자의 `users.signup_source`로 나눈다. UTM source/medium이 있으면 그것을, 없으면 외부 referrer의 도메인을, 둘 다 없으면 "직접·알 수 없음"으로 묶는다.

## 이 화면에 없는 것

| 지표 | 이유 |
| --- | --- |
| 방문자, 반송률, 견적 작성·가입 단계별 이탈 | GA4에만 있다. bidit `docs/FUNNEL_ANALYTICS.md` 참조 |
| 접속 기준 DAU·MAU, 재방문율 | 접속 기록이 없다 |
| PG사 검토 시작·거절 사유, 합의서 서명 완료율 | `rfp_pg_reviews`, `signing_contracts`가 이 앱의 스키마에 없다 |
| 매출, 거래액, 고객 획득 비용 | 수익·거래액·광고비 데이터가 없다 |
| 만족도 | 수집하지 않는다 |

## 구현

- 정의: `lib/metrics/compute.ts` (순수 함수), 제외 규칙과 활동 허용 목록: `lib/metrics/rules.ts`, 날짜 경계: `lib/metrics/periods.ts`
- 조회: `lib/server/queries/admin/metrics.ts`. 읽기 전용이고 `data.view` 권한을 먼저 확인한다. 추가 DDL은 없다
- 화면: `components/MetricsDashboard.tsx`

워크스페이스·멤버·요청·초대·견적·선정은 필요한 컬럼만 전체를 읽어 메모리에서 집계한다. 요청이 수만 건을 넘기면 SQL 집계로 옮긴다. bidit에 새 `audit_logs.action`이 생기면 `HUMAN_ACTIONS`에 추가해야 활동으로 잡힌다.

검증: `pnpm test` · `pnpm typecheck` · `pnpm lint`.
