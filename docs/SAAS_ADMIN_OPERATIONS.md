# 서포트비 통합 어드민 운영안

**첫 개발 과제로 ‘신청 진행 보드’를 추천한다.** 운영자가 구매사의 “어디까지 진행됐나요?”라는 문의를 받으면, 한 RFP에서 현재 PG사, 마지막으로 확인된 일, 다음에 움직일 사람과 기한을 찾아야 한다. 홈은 오늘 조치할 일을, 신청 보드는 거래 한 건의 진행을, 기존 **PG사별 현황** 탭은 여러 거래에 걸친 파트너의 응답을 맡는다. [현재 관리자 메뉴](../lib/admin-navigation.ts) · [메인 서비스의 신청 진행 보드 기획안](../../bidit/docs/research/2026-11-22-consultation-kanban-plan.md)

2026년 11월 22일 기준으로 제품사의 공식 문서, 관리자 저장소 `6c87b6bd91`, 메인 서비스 `bidit`의 `d8027cd143` 및 별도의 로컬 보드 기획안을 대조했다. 현재 기능은 코드 기준이고 보드의 신규 신청 유형은 기획 단계다. 두 저장소를 나란히 둔 작업 공간에서 내부 근거 링크를 열 수 있다. 우선순위는 운영 배포 현황과 상담량·처리 시간 실측 전의 제안이다.

## 첫 출시 전에 바로잡을 운영 표시

조사 당시 RFP 상세의 **‘전체 리마인더 발송’**은 초안과 재견적을 포함한 견적 행에서 PG ID를 모았다. 서버가 돌려준 건수는 이 배열의 길이였고, 실제로 남은 기록은 감사 로그 한 건이었다. 이 경로를 제거하고 기존 로그에는 ‘발송 미확인’을 표시했다. 현재의 수신자 확인과 발송 결과 조회 방법은 운영 가이드에 정리했다. [운영 가이드](ADMIN_GUIDE.md#신청-진행과-후속-업무)

**권고안**은 실제 발송을 연결할 때까지 버튼을 숨기는 것이다. 발송 기능을 열 때는 진행 중인 요청의 유효한 초대·상담과 제출 이력에서 후보를 구하고, 운영자가 수신처와 사유를 확인하게 한다. 조치 요청, 발송 대기열 등록, 공급자 접수, 수신 메일 서버 전달·반송, 서비스 안에서의 초대 열람을 각각 증거가 있는 시점에 표시한다. 결과가 불명확한 재시도는 공급자 기록을 먼저 대조한다. [Resend 이메일 이벤트 정의](https://resend.com/docs/webhooks/event-types) · [메인 서비스 발송 대기열의 재시도 기준](../../bidit/docs/OUTBOX_CLAIMS_ROLLOUT.md)

| **즉시 · 리마인더 표시 정정** | 감사 로그만 남기는 버튼의 발송 표시를 정리한다. 과거 로그의 의미도 ‘운영자가 조치를 요청함’으로 설명한다. | 발송 대기열이나 공급자 근거가 없는 건에 ‘발송 완료’가 표시되지 않는다. |
| **1차 · 읽기 전용 신청 진행 보드** | RFP 목록·PG사별 현황 옆에 보드를 두고, 기존 요청·PG 상담·견적·선정·서명 기록을 연결한다. 홈의 마감 임박 목록에서 동일한 상세로 들어간다. | 세 PG를 초대한 요청은 카드 한 장이다. A사의 재견적, B사의 열람 후 미제출, C사의 열람 기록 없음을 상세에서 구별한다. 마감 경과와 거래 종료를 따로 표시한다. 과거 담당자·첫 연락 시각이 없으면 ‘기록 없음’으로 보인다. |
| **2차 · 담당·인계와 고객 검색** | 업무에 ‘대상 회사/RFP/PG 회차, 내부 담당자, 다음 연락 시각, 할 일, 처리 결과’를 기록한다. 홈에 ‘미배정·오늘 할 일·기한 지남’을 두고 채널톡 상담과 연결한다. | 담당자가 자리를 비워도 동료가 마지막 연락과 다음 약속을 찾아 처리한다. 같은 PG의 재견적, 다른 PG로의 전환, 가입 전 문의가 서로의 업무를 덮어쓰지 않는다. |
| **3차 · 발송과 예외 처리** | 실제 발송 대상 미리보기, 중복 방지, 결과 조회를 붙이고 서명 동기화 지연·반송·조건 불일치에 담당자를 지정한다. | 같은 조치를 재시도해도 동일 수신자에게 중복 예약되지 않는다. 공급자 접수 여부가 불명확하면 ‘확인 필요’로 남는다. 조회 담당자가 발송·요율 변경을 시도하면 서버에서 차단된다. |

메인 서비스의 11월 22일 기획안에는 **즉시 견적·담당자 배정·기존 맞춤 상담** 세 흐름이 있다. 1차 보드는 현재 기록을 읽는 범위로 시작한다. 신규 흐름의 첫 연락 약속, PG 가입 결과, 실제 조건 적용 확인은 메인 서비스에서 저장을 시작한 건부터 표시한다. **서포트비 내부 담당자**와 **PG사의 상담 담당자**도 별도 항목으로 둔다. [신청 유형별 데이터와 출시 의존성](../../bidit/docs/research/2026-11-22-consultation-kanban-plan.md)

## 효과 확인

시범 운영 전후에 같은 유형의 건을 골라 운영자가 직접 확인한다. 우선순위를 조정할 때는 발생 빈도, 건당 소요 시간, 관여 인원, 오처리 영향을 함께 본다. [토스 내부 운영 도구팀의 사례](https://toss.tech/article/how-to-make-marvelous-productivity-with-well-made-system)

| 확인할 값 | 측정 기준 |
|---|---|
| 문의 한 건을 파악하는 시간 | 회사명 또는 RFP 코드를 받은 시점부터 **현재 단계·다음 담당자·기한**을 답할 때까지의 중앙값. 출시 전후 같은 유형의 문의로 비교한다. |
| 기한 안에 후속 연락을 처리한 비율 | 해당 기간에 연락 약속이 도래한 업무 중 기한까지 실제 연락 결과를 기록한 건수 / 약속이 도래한 업무 수. 견적 마감일은 이 계산에 쓰지 않는다. |
| 발송 결과 미확인·중복 건수 | 같은 발송 요청과 수신자를 기준으로 예약, 공급자 접수, 최종 결과를 대조한다. ‘미확인’과 확인된 중복을 별도 건수로 낸다. |
| 선정 후 서명 대기 건수와 경과일 | 신규 노온–구매사 합의서 대상으로 준비 중·발송 후 진행 중·완료를 구분한다. 과거 계약은 계약 종류별로 별도 조회한다. |
