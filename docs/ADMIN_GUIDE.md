# 관리자 운영·확장 가이드

## 현재 권한 정책

`ADMIN_EMAILS`에 등록되어 로그인한 계정은 모두 `super_admin`(최고 관리자)입니다. 별도 역할 배정은 필요하지 않습니다. 허용 목록에 없는 계정은 로그인할 수 없습니다.

현재 `ADMIN_SUPER_EMAILS`와 `ADMIN_ROLE_ASSIGNMENTS`는 사용하지 않습니다. 기존 환경에 해당 값이 남아 있어도 현재 역할에 영향을 주지 않습니다.

## 향후 운영자 확장

역할별 권한 정의와 화면·서버의 권한 검사는 유지합니다. 운영자 분리가 필요해지면 `lib/auth/admin-session.ts`의 역할 결정 부분을 계정별 역할 조회로 교체하면 됩니다. `lib/auth/permissions.ts`의 `assignedRole`은 그때 사용할 수 있는 역할 설정 파서이며 현재 세션에서는 호출하지 않습니다.

준비된 역할은 다음과 같습니다.

- viewer: 데이터·감사 이력 조회
- reviewer: 조회, 입점·이름 변경·담당자 심사, 메모 작성
- finance: 조회, 수수료·추천 기준 관리
- operator: 영구 삭제를 제외한 운영 업무
- super_admin: 영구 삭제를 포함한 모든 업무

역할 분리를 활성화할 때도 `ADMIN_EMAILS` 허용 목록 검사는 유지해야 합니다.

## 기능 확장

권한은 `lib/auth/permissions.ts`, 메뉴 그룹은 `lib/admin-navigation.ts`에서 정의합니다. 서버 액션에는 `requireAdminPermission`을 사용하고 화면에도 같은 `hasPermission` 정의를 적용합니다. 버튼 숨김만으로 권한을 검사하지 않습니다.

목록은 `lib/admin-list.ts`와 공통 목록 컴포넌트를 사용하며, URL 검색 조건과 정렬을 유지합니다. 기존 배열 조회 함수는 옵션 선택 등 내부 용도이며 대규모 목록 페이지에서는 페이지 단위 API를 사용합니다.

심사처럼 상태가 전이되는 작업은 트랜잭션에서 현재 상태와 대상 ID를 검증해야 합니다. 데이터 변경, 감사 이력, outbox 기록을 같은 트랜잭션으로 처리합니다. 새 관리 기능은 객체 이력의 작업명과 대상 링크도 등록하세요.

조회 전용 계정에도 현재 관리 데이터가 보입니다. 계정별 데이터 범위 제한이 필요한 경우 조회 조건에도 별도 정책을 적용해야 합니다.

## 운영 화면

- 주요 목록은 25건씩 표시합니다. 검색·상태·기간·정렬·페이지가 URL에 남으며 상세의 목록 링크로 돌아와도 유지됩니다. 날짜 필터는 한국 시간 기준이며 종료일 전체를 포함합니다.
- 심사는 신청별로 처리합니다. 최신 신청이 아니거나 화면을 연 후 다른 운영자가 처리한 경우 새로고침을 요구합니다. ‘처리 후 다음 대기 건’은 현재 목록의 검색 조건에 맞는 최신 신청 중 오래된 건을 선택합니다.
- 입점 심사 목록에서는 신청됨·심사 중인 항목을 선택해 공통 사유로 보완 요청할 수 있습니다. 결과에 처리/건너뛴 건수를 표시합니다.
- 변경 이력에서 처리자·시각·변경 전후 값·사유를 확인합니다. 과거에 기록하지 않았던 변경 전 값은 소급 복원되지 않습니다.
- 신규사업체 자동 승인 구매사는 승인 완료 목록에서 확인합니다. 출처는 ‘신규사업체 예외’이며 검증된 개업일·국세청 확인을 표시합니다. 보나페이 신규 조회는 사용하지 않지만 과거 ‘자동 확인’ 이력은 유지합니다. 승인 여부와 무관하게 성공한 APICK 원본은 별도 조회 이력에서 확인할 수 있으며 조회 성공과 자동 승인은 구분합니다. [자동 승인 표시·배포 순서](BUYER_AUTO_APPROVAL.md)를 참고하세요.
- 영구 삭제는 최고 관리자만 가능합니다. 영향받는 연결 데이터와 삭제를 막는 보존 기록을 먼저 확인하고 현재 대상 이름을 입력해야 합니다. 사용자에게 연결된 거래·메시지 등 보존 기록은 회원 삭제를 위해 연쇄 삭제하지 않습니다.

관리자 권한·목록 기능은 기존 테이블을 사용합니다. 영세 자동 승인 표시에는 메인 앱의 `grade_source` enum 추가 DDL이 선행되어야 합니다. 현재는 허용된 관리자 모두 최고 관리자이며, 역할 분리는 추후 세션의 역할 결정 부분을 연결해 활성화합니다.

## 견적 작성 여정

- `/guest-journeys`: 로그인 전 견적 작성의 여정 목록. 초안 ID·가입 이메일·구매사명, 상태, 한국 시간 시작일로 검색하며 25건씩 표시합니다.
- `/guest-journeys/[draftId]`: 최근 입력 답변·전체 행동 이력·오류 횟수·분석 식별자와 녹화 링크를 확인합니다. 행동은 관측 시각·ID 순서로 25개씩 표시하며, 동일 질문을 다시 작성한 기록과 완료 뒤 늦게 도착한 기록도 보존합니다.
- 조회 함수가 `data.view` 권한을 먼저 확인합니다. 초안 소유권 비밀값은 조회하지 않습니다. 기록은 기존 메인 앱의 30일 보존 정책을 따르며 보관기간이 지난 답변은 복구하지 않습니다. 마지막 관측 이후 활동이 없다는 이유만으로 이탈로 표시하지 않습니다.
- Slack에서는 10분 진행 요약과 서버 요청 완료 요약의 `여정 상세 보기`로 접근합니다. GA는 날짜·식별자로 사용자를 찾아야 하고, Clarity 링크는 재생 가능성을 보장하지 않습니다.
- 공유 DB에 메인 앱의 `20261020-guest-journey.sql`이 적용되어 있어야 합니다. 추가 DDL은 없습니다. 관리자 화면을 먼저 배포한 뒤 메인 앱의 요약 발송 변경을 배포합니다. 메인 앱 `ADMIN_ORIGIN`은 관리자 origin을 사용합니다.
