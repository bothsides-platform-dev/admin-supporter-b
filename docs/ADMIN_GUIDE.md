# 관리자 운영·확장 가이드

## 현재 권한 정책

관리자 계정은 공유 DB의 `admin_users` 테이블에 있고 **관리자 계정**(`/admins`) 화면에서 관리합니다. 여기 등록된 Google 계정만 로그인할 수 있고, 로그인한 계정은 모두 `super_admin`(최고 관리자)입니다. 별도 역할 배정은 필요하지 않습니다.

예전 `ADMIN_EMAILS`·`ADMIN_SUPER_EMAILS`·`ADMIN_ROLE_ASSIGNMENTS` 환경변수는 더 이상 읽지 않습니다.

## 관리자 계정과 2단계 인증

- 로그인할 때마다 Google 로그인 뒤 인증 앱(Google Authenticator, 1Password 등)의 6자리 코드를 입력합니다. 한 번 통과하면 12시간 동안 유지되고, 로그아웃하거나 Google로 다시 로그인하면 다시 입력합니다.
- 새 관리자는 `/admins`에서 이메일로 추가합니다. 추가된 사람이 처음 로그인하면 QR 코드가 나오고, 인증 앱에 등록한 뒤 코드를 입력하면 등록이 끝납니다. 미등록 계정은 그 Google 계정으로 처음 로그인한 사람이 등록하게 되므로 추가한 뒤 바로 등록하도록 안내하세요.
- 코드를 5번 틀리면 15분 동안 잠깁니다.
- 휴대폰을 잃어버렸거나 인증 앱을 지웠다면 다른 관리자가 `/admins`에서 **2단계 인증 초기화**를 누릅니다. 다음 로그인 때 다시 등록하며, 기존 2단계 인증 통과 상태도 바로 무효가 됩니다.
- 본인 계정의 삭제·초기화는 다른 관리자만 할 수 있고, 마지막 남은 관리자 계정은 삭제할 수 없습니다. 추가·삭제·등록·초기화는 감사 로그에 남습니다.
- 관리자 계정 관리 권한(`admin.manage`)은 최고 관리자에게만 있습니다. 아무도 로그인할 수 없게 되면 [배포 런북](DEPLOY.md#휴대폰-분실잠김-복구)의 SQL로 복구합니다.

## 향후 운영자 확장

역할별 권한 정의와 화면·서버의 권한 검사는 유지합니다. 운영자 분리가 필요해지면 `lib/auth/admin-session.ts`의 역할 결정 부분을 계정별 역할 조회로 교체하면 됩니다. 역할을 `admin_users`에 저장하려면 메인 앱(bidit) 스키마에 컬럼을 먼저 추가하고 공유 DB에 적용해야 합니다. `lib/auth/permissions.ts`의 `assignedRole`은 그때 사용할 수 있는 역할 설정 파서이며 현재 세션에서는 호출하지 않습니다.

준비된 역할은 다음과 같습니다.

- viewer: 데이터·감사 이력 조회
- reviewer: 조회, 입점·이름 변경·담당자 심사, 메모 작성
- finance: 조회, 수수료·추천 기준 관리
- operator: 영구 삭제를 제외한 운영 업무
- super_admin: 영구 삭제를 포함한 모든 업무

역할 분리를 활성화할 때도 `admin_users` 허용 목록 검사와 2단계 인증은 유지해야 합니다.

## 기능 확장

권한은 `lib/auth/permissions.ts`, 메뉴 그룹은 `lib/admin-navigation.ts`에서 정의합니다. 서버 액션에는 `requireAdminPermission`을 사용하고 화면에도 같은 `hasPermission` 정의를 적용합니다. 버튼 숨김만으로 권한을 검사하지 않습니다.

목록은 `lib/admin-list.ts`와 공통 목록 컴포넌트를 사용하며, URL 검색 조건과 정렬을 유지합니다. 기존 배열 조회 함수는 옵션 선택 등 내부 용도이며 대규모 목록 페이지에서는 페이지 단위 API를 사용합니다.

심사처럼 상태가 전이되는 작업은 트랜잭션에서 현재 상태와 대상 ID를 검증해야 합니다. 데이터 변경, 감사 이력, outbox 기록을 같은 트랜잭션으로 처리합니다. 새 관리 기능은 객체 이력의 작업명과 대상 링크도 등록하세요.

조회 전용 계정에도 현재 관리 데이터가 보입니다. 계정별 데이터 범위 제한이 필요한 경우 조회 조건에도 별도 정책을 적용해야 합니다.

## 운영 화면

- 주요 목록은 25건씩 표시합니다. 검색·상태·기간·정렬·페이지가 URL에 남으며 상세의 목록 링크로 돌아와도 유지됩니다. 날짜 필터는 한국 시간 기준이며 종료일 전체를 포함합니다.
- RFP 상세의 **PG사별 응답 현황**은 발송한 초대만 한 곳에 한 줄씩 보여줍니다. 견적이 없으면 ‘열람 기록 없음’과 ‘열람 후 미제출’을 구분합니다. 열람 기록이 없다고 초대가 전달되지 않은 것은 아닙니다. 견적이 있으면 초안을 제외한 마지막 제출 회차와 철회 여부를 표시하며, 모든 회차는 아래 견적 목록에서 확인합니다.
- **운영 현황 → PG사별 현황** 또는 RFP 목록의 **PG사별 현황** 탭에서 여러 RFP의 응답을 회사별로 비교합니다. 초대 발송일로 기간을 좁힐 수 있고, 해당 기간에 초대를 받지 않은 회사도 0건으로 표시합니다. 미제출 건수에는 마감된 RFP도 포함됩니다. ‘마감이 가까운 미제출 RFP’를 누르면 진행 중인 요청에서 해당 PG사의 행으로 이동합니다. 상세의 **PG사별 현황** 링크로 돌아오면 검색 조건과 페이지가 유지됩니다.
- 심사는 신청별로 처리합니다. 최신 신청이 아니거나 화면을 연 후 다른 운영자가 처리한 경우 새로고침을 요구합니다. ‘처리 후 다음 대기 건’은 현재 목록의 검색 조건에 맞는 최신 신청 중 오래된 건을 선택합니다.
- 입점 심사 목록에서는 신청됨·심사 중인 항목을 선택해 공통 사유로 보완 요청할 수 있습니다. 결과에 처리/건너뛴 건수를 표시합니다.
- 변경 이력에서 처리자·시각·변경 전후 값·사유를 확인합니다. 과거에 기록하지 않았던 변경 전 값은 소급 복원되지 않습니다.
- 신규사업체 자동 승인 구매사는 승인 완료 목록에서 확인합니다. 출처는 ‘신규사업체 예외’이며 검증된 개업일·국세청 확인을 표시합니다. 보나페이 신규 조회는 사용하지 않지만 과거 ‘자동 확인’ 이력은 유지합니다. 승인 여부와 무관하게 성공한 APICK 원본은 별도 조회 이력에서 확인할 수 있으며 조회 성공과 자동 승인은 구분합니다. [자동 승인 표시·배포 순서](BUYER_AUTO_APPROVAL.md)를 참고하세요.
- 영구 삭제는 최고 관리자만 가능합니다. 영향받는 연결 데이터와 삭제를 막는 보존 기록을 먼저 확인하고 현재 대상 이름을 입력해야 합니다. 사용자에게 연결된 거래·메시지 등 보존 기록은 회원 삭제를 위해 연쇄 삭제하지 않습니다.

관리자 권한·목록 기능은 기존 테이블을 사용합니다. 영세 자동 승인 표시에는 메인 앱의 `grade_source` enum 추가 DDL이 선행되어야 합니다. 현재는 허용된 관리자 모두 최고 관리자이며, 역할 분리는 추후 세션의 역할 결정 부분을 연결해 활성화합니다.

## 신청 진행과 후속 업무

- **RFP → 신청 진행 보드**에서 구매사명·요청 코드·참여 PG로 신청을 찾습니다. 카드는 접수된 RFP 한 건입니다. 견적 기한이 지난 열린 요청에는 ‘기한 경과’가 붙습니다. 카드를 열면 PG 상담 회차·사유와 노온–구매사 합의서의 확인 시각을 볼 수 있습니다. 과거 PG–구매사 계약도 종류와 회차를 표시합니다.
- **고객 검색**에서는 회사명, 사업자번호, 회원 이메일, RFP 코드로 찾습니다. 구매사·PG사·회원·RFP별 결과에서 상세로 이동하면 검색 목록으로 돌아갈 수 있습니다.
- **후속 업무**에서 할 일, 내부 담당자, 다음 연락 시각을 등록합니다. 회사나 RFP 상세에서 시작하면 대상이 자동으로 채워집니다. 견적 조건·계약·메일 결과를 확인할 때는 해당 회차에서 업무를 여세요. 가입 전 문의는 미연결로 등록한 뒤 회사 ID나 RFP 코드로 연결할 수 있습니다. ‘기록·인계·완료’로 연락 내용과 다음 약속을 남기고, 완료할 때는 처리 결과를 입력합니다. ‘연락·처리 기록’에서 이전 기록도 읽을 수 있습니다.
- 홈의 **오늘 할 일**은 한국시간으로 오늘이 연락일인 미완료 업무입니다. **기한 지남**은 다음 연락 시각이 지난 미완료 업무입니다. 오늘 오전에 놓친 연락은 두 목록에서 모두 찾을 수 있습니다.
- **RFP 상세 → 견적 마감 안내**에서 미제출 회차의 유효한 초대 또는 현재 맞춤 상담에 연결된 PG와 승인·이메일 인증을 마친 활성 담당자를 확인합니다. 수신자 선택과 내부 사유 입력 뒤 이메일을 예약합니다. 자동 마감 안내와 같은 키로 중복 예약을 막습니다. 상담 배정 대상 회차에서는 서비스가 현재 배정된 담당자에게 마감 안내를 보냅니다. 해당 회차의 담당자와 안내 이력은 RFP 상세의 **PG 상담 및 서명 이력**에서 확인합니다. 결과 확인에는 Resend 메시지 ID와 해당 메일의 수신자·태그를 사용합니다. 공급자 기록이 없는 과거 건은 ‘미확인’으로 남습니다. [Resend 이메일 조회](https://resend.com/docs/api-reference/emails/retrieve-email)
- **운영 반영 순서**는 메인 서비스 `bidit`의 `scripts/migrations/20261122-admin-followups.sql` 및 `20261122-reminder-receipts.sql` 적용, 메인 메일 처리기와 어드민 배포 순입니다. 메일은 메인 서비스의 기존 outbox 실행기가 처리합니다. 운영 이메일 결과를 조회하려면 어드민의 `RESEND_API_KEY`에 해당 Resend 계정의 조회 권한이 필요합니다. PG 링크에는 해당 환경의 `NEXT_PUBLIC_PARTNER_ORIGIN`을 사용합니다.

## 핵심 지표

- `/metrics`: 주간 추이, 구매사 퍼널, PG사 응답과 매칭, PG사별 현황, 행동 기준 활성 사용자, 가입 유입 경로를 보여줍니다. 기간은 최근 4·12·26·52주 중에서 고르며 기본은 12주입니다.
- 비율은 `분자/분모`로 표시하고 분모가 10 미만이면 퍼센트를 붙이지 않습니다. 진행 중인 요청은 비율에 넣지 않습니다.
- 시스템 계정과 테스트 워크스페이스는 집계에서 빼고 그 건수를 화면 아래에 표시합니다. 내부 직원 계정은 `METRICS_EXCLUDED_EMAIL_DOMAINS`에 도메인을 등록하면 함께 빠집니다. 담당자가 합류하지 않은 PG사는 신규·활성 수에만 넣지 않고, 받은 요청과 견적은 그대로 셉니다.
- 활성 사용자는 접속자 수가 아니라 기록이 남는 행동을 한 사용자 수입니다. 정의와 한계는 [핵심 지표 정의](METRICS.md)를 참고하세요.
- 조회 전용이며 추가 DDL은 없습니다.

## 견적 작성 여정

- `/guest-journeys`: 로그인 전 견적 작성의 여정 목록. 초안 ID·가입 이메일·구매사명, 상태, 한국 시간 시작일로 검색하며 25건씩 표시합니다.
- `/guest-journeys/[draftId]`: 최근 입력 답변·전체 행동 이력·오류 횟수·분석 식별자와 녹화 링크를 확인합니다. 행동은 관측 시각·ID 순서로 25개씩 표시하며, 동일 질문을 다시 작성한 기록과 완료 뒤 늦게 도착한 기록도 보존합니다.
- 조회 함수가 `data.view` 권한을 먼저 확인합니다. 초안 소유권 비밀값은 조회하지 않습니다. 기록은 기존 메인 앱의 30일 보존 정책을 따르며 보관기간이 지난 답변은 복구하지 않습니다. 마지막 관측 이후 활동이 없다는 이유만으로 이탈로 표시하지 않습니다.
- Slack에서는 10분 진행 요약과 서버 요청 완료 요약의 `여정 상세 보기`로 접근합니다. GA는 날짜·식별자로 사용자를 찾아야 하고, Clarity 링크는 재생 가능성을 보장하지 않습니다.
- 공유 DB에 메인 앱의 `20261020-guest-journey.sql`이 적용되어 있어야 합니다. 추가 DDL은 없습니다. 관리자 화면을 먼저 배포한 뒤 메인 앱의 요약 발송 변경을 배포합니다. 메인 앱 `ADMIN_ORIGIN`은 관리자 origin을 사용합니다.

## PG 상담 배정·지연

‘PG 상담 배정·지연’에서 미배정, 첫 연락·견적 지연, 미수신 판정 대기 건의 견적번호를 열 수 있다. RFP 상세에서 같은 PG의 활성 담당자를 골라 배정 사유를 남긴다. 구매사가 미수신으로 답한 질문에는 연락 인정 또는 연락 없음과 판단 근거를 기록한다. 배정·판정은 감사 로그에 남는다.

PG사명을 열면 합의 기한과 담당자 순서, 책임자, 시정 요청 집계 기간과 건수를 설정할 수 있다. 확정된 지연이 합의 기준에 도달하면 책임자와 메일 본문이 나타난다. ‘내용 확인 후 책임자에게 발송’을 누르면 서비스 앱이 수신 자격을 다시 확인해 메일을 보낸다. 같은 화면에서 발송 확정자와 메일 처리 결과를 확인한다. 공유 DB 마이그레이션은 서비스 저장소의 `scripts/migrations/20261122-pg-consultations.sql`을 사용한다.
